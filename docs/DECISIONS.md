# Decisions

## Foundation

- Target .NET 10, the installed current LTS, which satisfies the brief's .NET 8 or newer LTS requirement.
- Use the .NET 10 solution format (`.slnx`) generated by the installed SDK.
- Keep the MVP deployable as one ASP.NET Core API and one Blazor web app; PostgreSQL is the shared datastore.
- Serilog writes structured events to console and rolling local files. Production log retention and external aggregation remain deployment configuration.
- Readiness checks PostgreSQL connectivity; liveness only checks that the API process responds.
- The initial compose password is for local development only. Set `POSTGRES_PASSWORD` outside local development.

## Package choices

- `Npgsql.EntityFrameworkCore.PostgreSQL` provides EF Core's PostgreSQL provider and database connectivity required by the architecture.
- `Serilog.AspNetCore` integrates request and application logging; `Serilog.Sinks.File` adds the requested rolling local log output alongside console output.
- `Microsoft.Extensions.Diagnostics.HealthChecks` supplies the health check interfaces and registration used for PostgreSQL readiness.

## Milestone 2: Identity and tenancy

- Keep the user and membership tables aligned with the Section 8 schema. Organization roles are a PostgreSQL enum (`OWNER`, `MANAGER`, `CASHIER`) and use display casing in JWT/API responses.
- Passwords use ASP.NET Core Identity's `PasswordHasher<TUser>` without adding the full Identity user store; the requested schema uses its own UUID `users` table and membership model.
- Access tokens last 15 minutes and refresh tokens last 14 days. Refresh token plaintext is returned once; only its SHA-256 digest is persisted. Detecting a revoked token reuse revokes all remaining active refresh tokens for that user.
- Refresh requests accept an optional `organizationId`. Users with more than one membership must supply it at login or refresh so the tenant scope cannot silently change.
- OTPs use Identity's salted password hasher in the database. The development sender logs a masked phone number and the OTP to the console; it is not a real SMS integration.
- In addition to query filters, `FutsalDbContext.SaveChanges` rejects organization-scoped writes whose organization differs from the authenticated scope. Audit rows are immutable through EF updates/deletes.
- Development seeding runs only under `Development` and is skipped unless both seed passwords are configured in User Secrets. Default seed emails are non-secret local-only identifiers.
- There is no membership-management HTTP endpoint in this milestone. EF records `ROLE_CHANGED` audit entries when a membership role is changed by an authorized application operation; the seed Owner assignment is recorded as `ROLE_ASSIGNED`.
- Authentication and tenant tests use EF Core InMemory for repeatable local runs. Applying the generated migration and running database-backed integration tests require the machine-specific `ConnectionStrings:FutsalPro` User Secret.
- `Microsoft.AspNetCore.Authentication.JwtBearer` enables JWT validation; EF Design and Configuration provider packages support migration tooling and loading the API User Secrets for EF CLI commands; EF InMemory is limited to the xUnit test project.

## Locations and venue discovery

- The checked-out repository had no Milestone 3 venue, court, pricing, or public venue code despite the task stating that Milestone 3 was complete. To support this feature without touching booking scope, the implementation adds only the minimal venue/court listing data needed for location filters (including a per-slot price field); it does not implement bookings or Milestone 4.
- Location and amenity seed rows are inserted idempotently during Development startup. `is_seeded` is retained on location rows as a visible provenance flag; seeded names and Nepali spellings are initial editable catalog values.
- District rows are included to preserve the requested Province → District → City → Area hierarchy. Each requested major city is assigned to its commonly associated district and province; review/correct these editable mappings before public launch.
- An Owner may add an Area only beneath a City already referenced by one of that Owner's organization venues. This is the available project-level definition of “their own neighborhood”; location rows themselves stay global.
- Public city and area filters accept either the global location UUID or its slug. Public listing ignores tenant filters only for the venue query, then explicitly requires `is_public` and an active linked location; response projection contains no organization/customer fields.
- Venue coordinates are optional as a pair. If supplied, both must be inside Nepal bounds; missing coordinates are excluded from near/radius results.
- Near-me distance uses a server-side Haversine calculation after public and structured filters. The requested `radiusKm` is applied in memory; PostGIS indexing is deferred.
- Lowest price uses the minimum active court `price_per_slot`, since a pricing-rule calculator was absent from this checkout. Photo output is a placeholder field.
- The generated migration could not be checked against the local PostgreSQL database because the existing User Secrets did not provide a PostgreSQL password. `dotnet ef migrations remove` reported the connection error while safely removing the un-applied draft; the finalized migration was regenerated. Apply it after configuring the local connection secret.

## Milestone 4: booking engine

- The checkout did not contain the previously completed Milestone 3 operating-hours, blocked-period, pricing-rule calculator, or public availability pieces. Milestone 4 adds the minimum schedule and pricing-rule support needed by booking validation and price calculation, while retaining the existing venue/location implementation. This does not start SignalR or Milestone 5.
- Slot correctness is enforced by PostgreSQL GiST exclusion constraints for bookings and blocked periods. Application transactions also serialize writes per court with transaction-scoped advisory locks, expire overlapping stale holds, and translate PostgreSQL exclusion violations to HTTP 409 `SLOT_UNAVAILABLE`.
- Booking actions use an `IBookingNotifier` abstraction. The current implementation is intentionally a no-op because SignalR belongs to Milestone 5; persisted database state remains authoritative.
- Public availability returns court slot status and server-calculated price without customer information. Times are persisted as UTC and validated against venue-local hours in `Asia/Kathmandu` by default.
- Existing pricing did not include a rule calculator. The new calculator supports the specified weekday/time/date range and priority matching, and falls back to the existing flat `Court.PricePerSlot` when no rule matches.
- PostgreSQL integration and concurrency verification require `ConnectionStrings:FutsalPro` in API User Secrets and a separate local database named `futsalpro_test`; tests must never clean or migrate a database named `futsalpro` beyond the requested application migration.

## Milestone 5: real-time availability

- SignalR emits privacy-safe availability payloads to venue/date groups. Staff can join a separate group after the hub verifies JWT role claims and an active membership scoped to the venue organization and venue. Staff also receive a minimal `StaffBookingChanged` payload containing booking ID and slot state only; customer identity, booking code, and payment information remain excluded.
- Availability version stamps are SHA-256 hashes of the day’s active booking and block state, including the effective expiry of holds. This avoids another migration or mutable per-venue counter while giving clients a stable change detector.
- SignalR publishing is best effort and occurs after persistence. A durable outbox is not added in this milestone; clients recover missed messages with the version endpoint and periodic grid refetch.
- The prior checkout contained a blocked-period entity and availability reads but no write endpoints. Minimal Owner/Manager create/remove endpoints were added so blocked-period creation/removal can publish the required real-time events.
- Redis scale-out is optional and activates only when `Redis:ConnectionString` is configured. Without it, SignalR uses its default single-process lifetime manager.

## Milestone 7: eSewa payments and public booking

- **Payment Gateway Abstraction**: Defined `IPaymentGateway` with `InitiateAsync`, `VerifyAsync`, `CheckStatusAsync` in `Futsal.Application.Abstractions`. `EsewaGateway` implements this in `Futsal.Infrastructure.Payments`. Future gateways (Khalti, Fonepay) can plug in via `IPaymentGatewayResolver` without altering booking orchestration.
- **eSewa ePay v2**: Signature uses HMAC-SHA256 (Base64) over ordered `signed_field_names` (`total_amount`, `transaction_uuid`, `product_code`, etc.). Verification verifies signature using `CryptographicOperations.FixedTimeEquals` and calls eSewa status check API server-to-server.
- **Amounts Server-Controlled**: Clients never supply payment amounts. The advance amount is computed strictly on the server from `booking.AdvanceRequired` (or `TotalAmount` if 0).
- **Encrypted Per-Venue Settings**: Added `venue_payment_settings` with `EncryptedSecret` protected by ASP.NET Core Data Protection (`IVenuePaymentProtector`). Plain secrets are write-only and never exposed in GET responses or serialized DTOs. If a venue has no enabled online payment settings, online hold creation is rejected with `ONLINE_PAYMENT_DISABLED`.
- **Reconciliation & Late Payment Rule**: `PaymentReconciliationBackgroundService` runs every 2 minutes for `PENDING` payments older than 2 minutes. Under the late payment rule (AGENTS.md §7.6), if eSewa reports `COMPLETE` on an expired hold, the slot is checked: if still free, booking is confirmed late (`Booking.ConfirmLate()`); if taken, payment is marked `NEEDS_REFUND` with an audit log alert for manual staff processing.
- **Player PWA**: Built in `Futsal.Web` under `/v/...` with `PlayerLayout.razor`, location search/filters, live SignalR slot availability grid, hold countdown, OTP authentication modal, eSewa payment redirect callback, and "Add to Calendar" (.ics) download. App shell cached via service worker with no caching of availability or payment data.



## Milestone 8 — notifications and reports (2026-10-15)

- Scope is Milestone 8 only. Existing booking transactions, exclusion constraints, SignalR groups, payments, and public booking flow are preserved. No Milestone 9 work is included.
- Reuse post-commit booking events for confirmation/cancellation/payment notifications. A one-minute recovery scan handles missed event callbacks. Enqueueing uses a database unique key and `ON CONFLICT DO NOTHING`. Availability broadcasts happen before notification work, keeping SMS processing out of the live slot broadcast path.
- Notification settings/templates are seeded for existing venues by migration; new venues receive safe defaults on first settings/event access. Both English and Nepali template text comes from resources. An enablement timestamp prevents historical confirmations and payment receipts from being sent when the milestone is first installed. Existing future confirmed bookings can receive reminders.
- One PostgreSQL advisory session lock serializes sending across API instances. Queue insertion is independent of this lock. `notification_job_runs` persists reminder (5 minutes) and due (24 hours) schedules across restarts; queue sends and due retries run every minute. Retry delays are 2, 4, 8, 16, 32 minutes; the fifth failed attempt is terminal. Manual resend explicitly starts a fresh attempt budget for that failed record, and rechecks consent, phone, reminder validity, and caps.
- SMS delivery is at-least-once across process/network failures. A stable notification ID is supplied as the provider idempotency key. Exactly-once external delivery requires the chosen provider to support that key; confirm this before enabling HTTP sends. No software can atomically commit an external SMS delivery and a PostgreSQL transaction.
- Limits count SMS segments, not rendered messages. Reserve potential segment cost durably *before* each provider attempt; ambiguous failures therefore cannot bypass limits. `sms_usage.segments` is a conservative cost reservation; `delivered_segments` counts responses accepted by the configured provider contract. Monthly usage is the sum of Nepal-local calendar days. Provider billing reconciliation will still be needed for ambiguous outcomes.
- A capped message remains queued, with `SMS_CAP_REACHED`, a one-hour next attempt, and a persistent venue alert. Increasing limits clears the alert; the queued row is picked up when due. OTPs expire after five minutes rather than arriving late. Console sends are permitted only in Development. Queue payloads are Data Protection encrypted; successful OTP payloads are erased. Persist and protect the API Data Protection key ring in real deployments.
- Per-venue OTP templates/usage apply when an OTP request includes `venueId` (the public venue booking flow supplies it). Standalone account login has no venue, uses the platform English OTP template, and stores its queue row under reserved organization ID Guid.Empty with no venue usage charge. Venue customer opt-out is checked both when queueing and sending. Transactional messages only; no marketing sender is introduced.
- Nepal phones use the requested `+9779[678]` plus eight ASCII digits format. Staff booking input can retain its existing local-number normalization, but the SMS boundary only sends validated E.164 values. OTP phone throttling is serialized in PostgreSQL (three per rolling hour); the existing per-IP OTP limiter remains three per hour.
- Reports use parameterized PostgreSQL aggregation with explicit organization/venue predicates and server-side membership checks, including venue-scoped memberships. A Cashier can only read their own shift; Owner/Manager can select a cashier. Shift bounds are exact UTC instants corresponding to Nepal-local UI times, end-exclusive. All date ranges are inclusive local dates, converted to `[start, next-day-midnight)` UTC.
- Income is signed COMPLETED/REFUNDED payment entries at `verified_at ?? created_at`, including refunds on their actual transaction date. Pending/failed/refund-needed payments are excluded. Booking counts use booking start date and display each status; monthly booking value/count includes CONFIRMED/COMPLETED/NO_SHOW and excludes holds/cancellations/expired records. Thus a game crossing midnight belongs to its start day, while each payment belongs to its own Nepal transaction day.
- Dues are current nonnegative payable booking balances for bookings in the selected start-date range; cancelled/expired/held records are excluded. Debt age is whole days from the oldest included booking start to the report end, clamped to zero; last contact is the last successfully sent due notification in that venue. These are current balances, not historical point-in-time ledger snapshots.
- Utilization generates actual configured court slots in SQL, removes slots overlapping blocked periods, and counts those overlapping CONFIRMED/COMPLETED/NO_SHOW bookings. Holds are not utilization. Games crossing local midnight can occupy slots on either day. Active courts and current opening hours are used; historical schedule configuration is not versioned. Busiest/slowest ties use earliest date. Customer report rows include net payment spend, qualifying booking count, and no-show count, ordered by spend and bookings.
- Monthly comparison uses the selected date range shifted back one month. Where the previous amount is zero, percentage change is shown as zero with `NO_PREVIOUS_BASE`; it does not imply a mathematically defined percentage.
- Added QuestPDF 2026.7.0 for paginated PDF exports and bundled Noto Sans Devanagari (SIL OFL 1.1) for Nepali glyphs. QuestPDF uses a source-available commercial license: Community is free for eligible individuals/small organizations under USD 1 million annual gross revenue, plus qualifying charities/academia/open-source projects. Government/public-sector and publicly traded entities need a paid license (subject to stated academic exception). Configure Reports:PdfLicense after checking eligibility; Community is the development/default selection. See https://www.questpdf.com/license/guide.html and https://www.questpdf.com/pricing.html .
- Added NepDate 2.0.7 (MIT, no transitive dependencies) for shared table-based BS conversion; this replaces the prior approximate repeating-month display conversion. Added Testcontainers.PostgreSql 4.16.0 for tests against real PostgreSQL 16 and fresh migrations. These packages are justified by the requested PDF/BS behavior and real-database acceptance checks.
- Real PostgreSQL tests exposed that enum declarations in the EF model did not configure Npgsql runtime enum mapping. Added a shared provider configuration for runtime, design-time migrations, and PostgreSQL tests; no database enum values or booking overlap rules changed.
- Optional Owner SMS alerts for NEEDS_REFUND are omitted; the existing admin refund alert screen remains the staff alert channel. The SMS provider cannot be live-tested until the merchant supplies its endpoint/credentials and confirms the adapter contract.


## Milestone 10 — pilot tools (2026-10-15)

- Scope is pilot tooling only: no deployment, venue onboarding messages, Phase 2 modules, or real gateway/SMS calls were performed. Existing milestones remain in place.
- The Owner wizard saves one tenant-scoped JSON draft, serializes saves/finalization with a PostgreSQL advisory transaction lock, and validates before atomically creating venue, courts, hours, pricing and invitations. Existing organizations with venues are considered already set up. Optional eSewa credentials stay out of the resumable draft and use the existing encrypted settings endpoint after finalization. If that optional save fails, retry through Payment settings; cash bookings remain available.
- Weekday hours apply to every newly created court; closed days are unchecked. Default court prices suffice without an override. Rule court indexes start at zero. This keeps the pilot wizard small while using the existing settings for later edits.
- Staff invitations are manually shared, single-use, cryptographically random links with a seven-day expiry; only hashes are stored. Tokens travel in a URL fragment, which the browser removes on reading. Invitations create new Cashier/Manager accounts with the existing password policy. Existing-account reassignment is deliberately rejected rather than overwriting credentials or changing another tenant's access.
- CSV supports UTF-8, English/Nepali template headers, quoted commas/newlines, at most 48 KiB/200 data rows and 2,048 characters per cell. Local mobile numbers normalize to +977; valid prefixes are 96/97/98. Formula-leading customer names are rejected, and preview/report cells are prefixed safely for spreadsheet use. No raw HTML is rendered.
- Future booking CSV timestamps require Z or an explicit offset (Nepal: +05:45). Court name must identify exactly one visible court, otherwise use its UUID. Imported money is a decimal cash receipt, never an externally verified gateway payment. Prices are computed by the existing booking service. Each committed row uses its own normal booking transaction, database exclusion constraint and SignalR events. Conflicts are reported rather than forced. Preview reserves nothing and is advisory; every row is revalidated on commit. A stable import run ID plus row index makes booking retries idempotent. Successful rows stay committed if later rows fail; aggregate import outcomes are audited.
- Screenshot support intentionally accepts only structurally validated non-interlaced 8-bit RGB/RGBA PNG (192 KiB compressed, at most 2,073,600 pixels, maximum 1,920 per dimension). CRC, chunk boundaries and bounded decompression are checked, ancillary metadata is stripped, and SVG/HTML/other formats are rejected. This is a safe-type scan, not a claim of third-party antivirus scanning. Bytes remain in PostgreSQL with tenant filters, never in public static storage. Only staff in the submitting organization and SuperAdmin can read them. Feedback remains usable in subscription read-only mode.
- Demo organizations carry an immutable-through-normal-management IsDemo flag. SMS suppression occurs before payload decryption/provider invocation; payment initiation, verification and reconciliation check the organization before resolving a real gateway. Demo creation provides a random Owner login shown once to SuperAdmin for a separate browser session. Reset is SuperAdmin-only, checks IsDemo, replaces fictional customers/bookings/payments and restores sample hours/pricing. Existing demo login and immutable audit history remain. It cannot target a real tenant; normal real-tenant payment immutability is unchanged.
- Monitoring uses the last seven Nepal-local calendar dates, with current booking states grouped by scheduled date; source shares use that same denominator. SMS/payment counters cover records created in that window. Last login comes from LOGIN_SUCCEEDED audit entries. API 5xx counts are best-effort, tenant-attributed entries containing only correlation ID and UTC time; anonymous failures and outages preventing database writes remain visible in structured logs rather than an invented per-tenant count.
- The overlap watchdog runs at startup then polls every five minutes, performing at most one durable check per organization per 24 hours under a shared advisory lock. Active means every booking except CANCELLED/EXPIRED, matching the database constraint. Missing first-check evidence is shown as pending. Any nonzero count is a critical dashboard alert. Production never bypasses the exclusion constraint; only an isolated integration test temporarily removes it and restores it in finally.
- Repeated authenticated HTTP requests exposed a pre-existing Npgsql enum-mapping issue: creating a fresh translator per context created unbounded EF internal providers and failed after twenty. Reuse a static translator; the HTTP role matrix verifies repeated requests now succeed without suppressing warnings.
- No new NuGet dependencies. English/Nepali resource parity is checked by the existing localization test; machine-written Nepali needs human review (docs/pilot-translation-review.md). Actual owner training, professional translation review, production pilot observations and the two-week zero-double-booking outcome require real participants and are not claimed by automated tests.

Milestone 10 verification: `dotnet build` passed with zero warnings/errors; `dotnet test --logger "trx;LogFileName=milestone10.trx"` passed 129/129 tests with none skipped, including all prior tests and the 50-parallel-holds regression. `dotnet ef migrations has-pending-model-changes --project src/Futsal.Infrastructure --startup-project src/Futsal.Api --no-build` reported no pending model changes. `git diff --check` passed. New route authorization, imports, demo suppression/reset, watchdog, privacy, onboarding/invitation and login-routing tests passed. No production rollout or real provider send was attempted.
